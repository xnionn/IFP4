Тема: файлы, потоки и сериализация в C#

1. Какие ошибки были в исходной программе?

File.WriteAllText(path, line) каждый раз перезаписывает файл, поэтому после
второй регистрации первая исчезает. File.ReadAllText(path) выбрасывает
FileNotFoundException, когда файла ещё нет. Перевод строки в имени разбивает
одну регистрацию на несколько физических строк: имя не экранируется.
Наконец, строковое представление DateTime.Now зависит от текущей культуры.
StarterDiagnosis.Run воспроизводит все четыре проблемы; исходный код сохранён
в Starter/AttendanceLog.cs. Отсутствие JSON и интерфейса я не называю ошибками
исходника: это отдельные требования следующих заданий.

2. Почему AttendanceEntry — record, и что здесь означает неизменяемость?

Это sealed record AttendanceEntry(string Name, DateTimeOffset CheckInTime).
Позиционные свойства имеют init вместо обычного set, поэтому существующее
значение нельзя изменить присваиванием после инициализации. string неизменяем,
DateTimeOffset является значимым типом. Выражение with создаёт другой record.
Record также даёт сравнение по значениям, полезное при проверке результатов.
DateTimeOffset сохраняет время вместе со смещением относительно UTC.

3. Какой текстовый формат выбран и почему он надёжен?

Каждая строка содержит время в формате O, затем табуляцию, затем имя как
JSON-строку. Пример: 2026-10-03T09:00:00.0000000+05:00, табуляция,
"Alimzhan Almukhambetov". CultureInfo.InvariantCulture исключает зависимость
от настроек компьютера. JsonSerializer экранирует кавычки, обратные слеши,
табуляцию и переводы строк внутри имени. Поэтому запятая или перевод строки
в имени не нарушает границы записи. Deserialize применяет тот же формат.

4. Почему функции преобразования можно назвать чистыми?

AttendanceTextFormat.Serialize принимает запись и возвращает строку;
Deserialize принимает строку и возвращает запись. Они не открывают файлы,
не читают часы и не изменяют внешнее состояние. Для одинакового входа результат
одинаков. В Task 2 я проверяю преобразование туда и обратно прямо в памяти;
автоматические проверки дополнительно меняют культуру и специальные символы.
TextLogStore вызывает эти функции для каждой записываемой и читаемой строки.

5. Чем файл отличается от потока и сериализации?

Файл — сохранённые данные по определённому пути, например attendance.json.
Поток — объект для последовательного чтения или записи байтов; в JsonStore
используется FileStream. StreamWriter и StreamReader переводят текст в байты
UTF-8 и обратно поверх файлового потока. Сериализация — преобразование
AttendanceEntry в сохраняемое представление: строку собственного формата либо
JSON. Десериализация восстанавливает записи из этого представления.

6. Где видно, что интерфейс позволяет заменить хранилище?

Функция Demonstrations.AppendAndShow получает IAttendanceStore и вызывает
только store.Append(entries) и store.Load(). RunAll передаёт ей сначала
new TextLogStore(textPath), затем new JsonStore(jsonPath). Код функции при этом
не меняется. RunPipeline использует её же при каждом запуске. Клиенту нужен
общий контракт; конкретный класс выбирает способ работы с файлом.

7. Почему Append реализован по-разному для текста и JSON?

В тексте можно открыть StreamWriter с append: true и добавить новые строки.
В JSON хранится один массив. Дописать ещё один массив в конец означало бы
получить неправильный JSON. JsonStore загружает старые записи, присоединяет
новые, сериализует общий массив во временный файл и заменяет целевой файл.
Обе реализации сохраняют порядок и каждое переданное вхождение. Для N байтов
новых данных текстовое добавление требует O(N), а JSON при M байтах старых
данных — O(M + N), поскольку весь массив читается и записывается заново.

8. Как предотвращаются потеря данных и незакрытые дескрипторы?

Перед открытием файла входная последовательность полностью материализуется
и проверяется. Ошибка ленивого перечисления не записывает половину пакета.
Потоки находятся внутри using и закрываются при выходе, включая исключения.
Load полностью читает записи до возврата результата, поэтому у вызывающего
кода не остаётся открытого файла. JSON заменяет старый файл только после
успешной записи и закрытия временного; finally очищает временный файл.
Ограничение: аппаратная ошибка во время текстового добавления может оставить
часть нового пакета. using обеспечивает освобождение ресурса, а не откат.
Также решение предполагает одного писателя, без параллельных транзакций.

9. Как доказать, что данные сохраняются между запусками и не дублируются?

После dotnet build выполнить два отдельных процесса:
dotnet run --no-build -- --run 1 artifacts/my-defense
dotnet run --no-build -- --run 2 artifacts/my-defense

Каталог должен быть новым или пустым до первого запуска. Первый запуск
создаёт по две записи, второй добавляет ещё две разные записи. Проверяется
совпадение результата с ожидаемой последовательностью и между хранилищами:
сначала 2, затем 4 записи, Duplicate entries: 0. Повторный запуск одной и той
же демонстрации в заполненном каталоге отклоняется. Сам Append не выполняет
дедупликацию: если намеренно передать одинаковую запись дважды, он сохраняет
два вхождения. Это соблюдение входных данных, а не случайное дублирование.

10. Что показать в проверках и какое изменение можно сделать на защите?

Команда dotnet run --no-build -- --checks запускает проверки обычной записи,
пустого и отсутствующего файла, специальных символов, культуры, сохранения
смещения времени, повторных добавлений, ленивого ввода, неверных данных,
блокировки файла и освобождения ресурсов. Отсутствующий файл даёт пустой
результат; повреждённый файл даёт исключение, а не маскируется под пустой.

Пример небольшого изменения: показывать только записи после заданного времени.
После store.Load() можно добавить Where(entry => entry.CheckInTime >= cutoff).
Фильтруется вывод, сохранённые данные не удаляются, обе реализации остаются
взаимозаменяемыми. Если преподаватель попросит добавить Email в модель, нужно
изменить record, обе функции текстового формата, примеры и проверки, а также
оговорить совместимость уже сохранённых файлов. JSON использует модель при
сериализации, но старые записи без нового обязательного поля потребуют решения.
